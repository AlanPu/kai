## 1. 路由 / 端点清单

### 1.1 WebSocket 端点（2 条）

### 阶段 F：用户回合循环
- **浏览器按住空格**：`pttDown` (index.html:596) 开始上行音频 → `_recv_loop` 收 bytes (server.py:748-749) → `sess.push_audio` (session.py:247)

### 阶段 G：Qwen 事件分发（session.py:368 `_on_qwen_event`）
- `error` (370-406)：先 `is_turn_race_error` 忽略可自愈 (379-382)；再 `is_recoverable_error`→置 `_want_rotate` (389-396)；`is_fatal_error`→置 `fatal_error` 并 `raise SessionFatal` (398-405)

- `speech_stopped` (445-472) → 仅置 `_user_speaking=False`，**不触发接话**（PTT 模式下断句由用户决定）
- `response.created` (474-478) → `_model_speaking=True`、`touch()`、清 pending
- `response.done` (480-489) → `_model_speaking=False`、`touch()`（从此刻算冷场）、`verifier.reset()`

### 阶段 H：转写、纠错、画像（session.py:576-661）
- `_on_user_text` (576-597)：`db.add_turn` (580) → 回推 `user_text` (582)；异步起 `_correct` (585-588)；累积 5 句后起 `_extract_profile` (591-597)

### 阶段 I：轮转看护（server.py `_timer_loop` 814-856）
每 5 秒轮询：
1. `sess.wants_rotate()` → `rotate_context()` (822-831)，失败发 `rotate_failed`
2. `sess.is_connection_lost()` → `raise SessionFatal` (836-838)
3. 发 `tick` (845-853)

`rotate_context` (session.py:693-766)：先清 `_want_rotate`(705) 防每 5 秒重试；取最近 12 轮生成承接语 `carry` (714-723)；关旧连 (726-728)；建新 `RealtimeSession` 带 `instructions+carry` 并连接 (731-741)；重置计数 (744-748)；**重新触发说话**(753-760)，否则轮转完一片沉默；发 `context_rotated` (762-765)。

### 阶段 J：收尾（server.py:710-740 + session.py:210-243）
1. 取消 pending 任务 (710-712)

3. 若 `fatal`：先发 `aborted` 带可读原因 (717-722)
4. 发 `finished` + `_build_report(sid)` (725-726) —— 直接读库不经 HTTP 层
5. `finally` 关 WS (736-740)

## 3. 「按 C 求援」(IDLE_NUDGE_MAX) 全链路

### 3.1 配置
- `.env.example:47` `IDLE_NUDGE_MAX=6`
- `Settings.idle_nudge_max` 默认 6 (core/config.py:71)
- `load_settings` 读取并容错 (config.py:116-120)：非数字/负数退回 6
- `ConversationSession._max_nudges = getattr(self.s, "idle_nudge_max", 6)` (session.py:141)

### 3.2 浏览器 → WS
- 判定函数 `isPromptKey` (index.html:661)：用 `event.code === "KeyC"`，理由同空格——不受输入法/大小写影响
- `keydown` 监听 (index.html:643-654)：`typingInField()` 让路(645)；要求 `running && !paused && ws.readyState===1`(646)；忽略长按 `e.repeat`(647)；放过 ⌘C/Ctrl+C(648)；`e.preventDefault()`(649)；**按住空格时不响应**(651)；最终 `ws.send({type:"prompt"})` (652) + 提示"让 AI 找话题…"(653)

### 3.3 WS → 服务器
- `_recv_loop` 收 text → `json.loads` → `_handle_cmd` (server.py:750-755)
- `_handle_cmd` `prompt` 分支 (server.py:796-799) → `await sess.prompt()`

### 3.4 `prompt()` (session.py:857-877)
1. `idle = self.idle_seconds()` (863) —— 暂停期间返回 0（`idle_seconds` 807-811）
2. `instr = self.maybe_prompt()` (864)；为 None 则直接 `return False` (865-866)
3. `maybe_prompt()` (813-836) 三道守卫：
   - `_model_speaking` 或 `response_pending()` → None (829-830)：AI 正在说话/准备说话，别插嘴
   - `_nudges_sent >= _max_nudges` → None (831-832)：本轮问够了
   - 否则 `_nudges_sent += 1`、`touch()`、返回指令 (834-836)
4. `_nudge_instruction()` (838-855)：第 1 次温和换角度追问；第 2 次起引入新话题。共同前缀禁止"你还在吗"和为沉默道歉
5. `_mark_response_pending()` (868) 置 pending 去重 → `rt.request_response(instructions=instr)` (869)
6. 发 `{"type":"ai_prompted","idle_sec":...}` (870) 并记日志 (871-872)
7. 异常则清 pending + `return False` (874-877)

`ai_prompted` 在 index.html:757 处理：提示"AI 接话了…"，让用户确认不是按错。

## 5. 分层规则的强制方式

README.md:122-123 声明："分层是**测试强制**的：`core` 不能 import `services`，`services` 不能 import `api`。违反会直接测挂。"

**强制点**：`tests/test_stage6_reliability.py:1000-1043` 的 `test_layering_is_enforced()`

机制：
1. `imports_of(pkg)` (1008-1030)：`rglob("*.py")` 遍历包内所有模块，`ast.parse` 后 `ast.walk` 收集 `ast.Import` 和 `ast.ImportFrom`。相对 import（`node.level>0`）通过 1022-1026 拼成绝对包名
2. `forbidden` 字典 (1032-1035)：
   ```python
   "app/core":     ("app.services", "app.api"),
   "app/services": ("app.api",),
   ```
3. 前缀匹配判定 (1039)：`name == bad or name.startswith(bad + ".")` → 记为 violation
4. 断言 (1043)：`assert not violations, "破坏分层：\n  " + ...`

测试上方注释 (990-997) 揭示了历史：README 早就写了"分层由测试强制"，但**其实没有任何测试在管**，规则只靠自觉；这个测试是补上的。

相关补充测试：`test_session_fatal_defined_in_core`(test_stage6_reliability.py:237-245) 断言 `SessionFatal.__module__ == "app.core.realtime"` —— 注释 239-242 说明它最初定义在 services，导致 core.realtime 反向导入（违反分层），故下移到 core。

代码中实际遵守情况（抽样验证）：server.py:25-39 同时导入 core/services/storage（api 在最上层，合规）；session.py:19-30 只导入 core/storage/同层 services（不碰 api，合规）。

## 6. 非显然细节 / 踩坑与变通

### 6.1 日志与全局单例
- `logging.basicConfig` (server.py:46-49)：注释 43-45 说明**不配的话 `log.info` 永远不显示**，排查轮转/画像时会误以为"没执行"
- `settings()` 惰性单例 (77-102)：网页选的音色压过 `.env`，写入 `data/voice_override.txt`；删掉该文件可恢复。注释 81-90 解释动机：用户点完音色界面显示"已切换"，重启却悄悄变回去 = "点了没用"
- `Settings` 是 frozen，`select_voice` 用 `dataclasses.replace` (server.py:327) 而非直接改

### 6.2 声纹判定未知的处理（最严重的坑）
session.py:295-320，注释 296-317 详述：
- 声纹要攒满 `window_sec`(2秒) 才出判定，所以每句话前 2 秒必然落在"未知"
- 原先压着不发等兜底阈值，后果：用户开口后 2 秒 Qwen 收不到声音 → 成批补发成碎片 → VAD 把碎片末尾当"说完了" → 突然回应并打断
- 顺带发现原兜底 `MAX_PENDING=100 块 × 8ms = 0.8秒 < 2秒声纹窗口`，永远算错
- 修正：判不出来就**直接放行**。声纹只用来否决，不用来放行（318-319）

### 6.3 touch() 不能无条件调用
session.py:264-272：麦克风上行连续，即使 PTT 模式松手前后也有零散静音块。若每块都 touch，冷场计时永远被重置。只有**检测到真实人声**（`rms > VOICE_RMS_FLOOR`）才 touch（291/345）。

### 6.4 response_pending 必须能超时复位
session.py:165-170，注释：
- 发了 `response.create` 但服务端**根本没产生 response**（半句话/音频太短/空缓冲），`response.done` 永远不来，"等待中"一直挂着 → 之后所有回合被当重复静默丢弃 → "用户说什么 AI 都不理"
- 解法：记录发起时刻，`response_pending()` (770-788) 超时 12s 即作废
- 边界：`since==0` 说明外部直接置位，按"刚刚发起"处理 (780-782)

### 6.5 speech_started 曾写错导致死锁
session.py:426-433：曾写成 `_model_speaking = True`。但 `push_audio` 在该标志为真时丢弃所有音频（275-276），而该标志只在 `response.done` 复位 → 用户说第一句后再也不能说话 → 不产生 response → 永远等不到 response.done → 死锁。正确语义：speech_started = 轮到用户，AI 闭嘴。

### 6.6 轮转必须在 recv 回调之外
- server.py:819-821：`_timer_loop` 里做轮转，**不能在 Qwen 的 recv 回调里做** —— 那里关连接会掐断正在执行回调的接收循环，异常冒泡整个会话被判异常结束（实测踩过）
- session.py:390-392 / 420-421：事件回调里只置 `_want_rotate` 标志，真正重连由外部循环执行
- `test_rotation_is_not_triggered_inside_recv_callback`(test_stage6_reliability.py:652) 守护

### 6.7 阈值标定的实测数据
session.py:38-54：
- Qwen 每会话最多 320 条 audio item，超出报 `InvalidParameter: Too many audios` 并断线；**实测约 12.5 分钟撞到**
- 我方只数 `input_audio_buffer.committed`，服务端计全部（含 AI 输出 item 和 VAD 碎片）
- **30 分钟实测：服务端报 320 时我方只数到 91**（约 3.5:1）
- 阈值取 `AUDIO_ITEM_ROTATE_AT = 60`（约对应服务端 210，留 110 余量）。注释 52-53：早转代价 1~2 秒停顿，撞上限代价是断线，不对等——宁可早转
- 阈值 150 那次失败（报错时才数到 91）—— 注释 47-49 有记录
- `test_audio_item_rotate_threshold`(test_stage6_reliability.py:~580-596) 断言 `30 <= ROTATE_AT < 91`

### 6.8 致命错误的暴露链路（三重保护）
1. `RealtimeSession._recv_task` 挂 `add_done_callback(_on_recv_done)` (core/realtime.py:196)：注释 190-195 说明 fire-and-forget 任务的异常会静静存在 task 对象里，上层以为连接还好着 → **实测空转 24 分钟**
2. `ConversationSession.is_connection_lost()` (session.py:665-685)：注释 672-676 说明 `SessionFatal` 没人 await，异常只存在 task 里。判据用 `task.done()` + `not rt.closed`，**故意不看 `rt.ready`**（那个标志 close() 里也会清掉，会把正常收尾误判成异常掉线）
3. `_timer_loop` 每 5 秒检查 (server.py:836-838)：连接死了就 `raise SessionFatal` 结束会话，不能继续发 tick 假装正常

### 6.9 SessionFatal 必须透传，不能降级
core/realtime.py:357-361 和 374-380 两处：其他异常记 warning，但 `SessionFatal` 必须 `raise`。注释：吞掉的话接收循环不终止，会话一直挂着 → 用户看到"报错了但画面卡住不动"。

### 6.10 无 type 的错误帧
core/realtime.py:338-364：额度耗尽时服务端回 `{"code":"AllocationQuota.FreeTierOnly","message":"..."}` **不带 type**，然后直接掐断。判据收紧到"必须有 code"（335-337）——正常帧偶尔也带无关 message，只凭 message 会误报。

### 6.11 FATAL_CODES 里移除了 invalid_request_error
core/realtime.py:96-102：它太笼统，"commit 空缓冲"这种客户端小失误也归进来 → 一次误触发打死整场会话。真正不可恢复的（额度/鉴权/过期）已单列。

### 6.12 可恢复错误必须先于致命判断
session.py:386-389：`Too many audios` 的 code 是 `InvalidParameter`（本身不在 FATAL_CODES），但消息里才带该串。注释明说必须**先** `is_recoverable_error` 再 `is_fatal_error`。`test_recoverable_is_checked_before_fatal`(test_stage6_reliability.py:611-620) 用源码 index 比较顺序。

### 6.13 asyncio.wait 不抛异常
server.py:691-692：`asyncio.wait` 只是"返回"完成的任务，必须逐个取 `t.exception()`（693-708），否则真实错误被静默吞掉。

### 6.14 `_StopRequested` 专用异常
server.py:780-782：不复用 `WebSocketDisconnect`（后者语义是"连接意外断开"，拿来当控制流会掩盖真实错误）。

### 6.15 close() 可能挂住
- core/realtime.py:386-394：`ws.close()` 实测 >8s 不返回（要等对端 close 帧，对端可能已不理我们）。必须限时（`timeout=5.0`），超时就强制断开
- session.py:218-225：关连接异常必须兜住，否则报告发不出、前端永久停在"正在生成报告…"转圈
- session.py:236-243：落库失败也不该挡住用户看报告（逐条发言已存）

### 6.16 浏览器端 stopPlayback 不能用 ctxOut.close()
index.html:452-458：`close()` 是异步的，紧接着新建的 AudioContext 在部分浏览器会 suspended → AI 语音再也播不出（用户反馈"我听不到 AI 语音"）。正确做法是只停播放源，保持 ctxOut 可用。

### 6.17 user_speaking 不再触发 stopPlayback
index.html:706-712：原来一收到 VAD 的 `user_speaking` 就掐 AI 声音，但 VAD 对噪声、甚至 AI 自己的尾音都可能触发 → AI 刚开口就被打断。现在抢话打断只由 `pttDown`（按下空格）这个明确动作触发。

### 6.18 enroll 接受两种 cmd 键名
server.py:954-957：前端发 `{"type":"end"}`，早期脚本发 `{"cmd":"end"}`。两个都认 —— 曾只认 `cmd`，导致网页点「读完了」被静默忽略（不报错不回应，看起来"点了没反应"），而脚本测试一切正常。

### 6.19 numpy dtype 必须显式指定
server.py:942-944：直接喂 bytes 会被 numpy 当 uint8，特征提取器当字符串解析报错 → 必须 `np.frombuffer(..., dtype=np.int16)`。

### 6.20 /api/stats 的变量名陷阱
server.py:392-394：⚠️ 变量名不能叫 `u` —— 上面那个 `u` 是用户对象，被循环覆盖后下面的 `u.id` 变成 Usage 对象的属性，整个 `/api/stats` 直接 500（「历史」按钮因此打不开）。

### 6.21 暂停机制（规避 Qwen 300 秒空闲关闭）
- 起因见 session.py:119-122：Qwen 在 300 秒无有效语音输入后关闭会话，而 30 分钟练习中途离开几分钟很正常
- `pause`/`unpause` (881-894)，`elapsed()` (896-903) 扣除暂停时间，`remaining_sec()` (905-907) 用 elapsed 而非直接减 started_at
- WS 命令 `pause`/`resume` (server.py:804-811)
- 暂停期间 `push_audio` 直接丢弃 (261-262)，避免重置 Qwen 空闲计时
- 前端 `window.blur` 兜底松开空格 (index.html:680)：切走标签页 keyup 收不到会导致麦克风一直开着

### 6.22 PTT 尾巴延迟
index.html:567-571：松开后等 `PTT_TAIL_MS = 250ms` 再断句 —— 麦克风音频分块上行带缓冲，松手瞬间最后几十毫秒还在路上，立刻断句会吃掉句尾。

### 6.23 end_turn 的 commit 判据
session.py:524-527：判据是 `_turn_audio_blocks`（push_audio 累加），**不是**对比 flush 前后的计数差 —— 声纹关闭时音频在 push_audio 阶段就直接送出了，flush 阶段一块都没有，用差值永远得 0（踩过）。

### 6.24 静音不能清空声纹缓冲
session.py:284-285：浏览器降噪会把句间停顿压得很低，一旦清空就永远攒不满 1 秒（真实踩过的坑）。

### 6.25 response.done 后清 verifier
session.py:487-488：AI 说完清空声纹缓冲，避免把自己的尾音算进判定。

### 6.26 前端断线处理：明确告知而非静默重连
index.html:671-678 `ws.onclose`：断线后 AI 上下文已没，`showDropped(code)` (869-896) 明确告知并给「继续练习」/「就此结束，看报告」两个选择。注释 675-677：静默重连会让用户以为还在接着聊，其实已经重开。
`resume()` (898-915) 用同一段内容重开，话题规划重跑；`reconnects > 3` 时提示检查网络 (900-902)。
`finishNow()` (917-924)：断线后无法通过 WS 收尾，直接拉取已保存的记录。

### 6.27 致命错误的用户文案
`_fatal_message` (server.py:758-777) 分档：idle / quota / api_key / rate / expired / 默认。注释 765-767：免费额度用完后阿里云会提示两种出路，不告诉用户他只能一脸茫然地反复重试。
前端 `aborted` 处理 (index.html:788) → `showAborted(reason, message)` (838-867)，提供「重新开始」/「看报告」。

### 6.28 启动相关的注释
- `__main__.py:19-24`：HTTPS 不是可选项（浏览器只在 localhost 或 https 下给麦克风权限）。注释明说"之前文档里写了 `--ssl-keyfile`，但代码根本没实现，照着做只会启动失败。现在补上"
- `__main__.py:46-49`：启动时打印生效模型。理由：配置错了不会立刻报错，往往练到一半才发现
- `__main__.py:58-59`：`idle_nudge_max > 0` 时打印"按 C 求援 一轮最多 N 次"，否则打印"已关闭"
- `__main__.py:35-37`：显式给了证书路径就等于要 HTTPS，不必再写 `--ssl`
- `run.py:14-18`：单独放这个文件是因为很多人习惯敲 `python server.py`，原型期 server.py 已删，敲错会得到"can't open file"看起来像工程坏了
- `start.sh:12-25`：比 `pkill && python` 多做四件容易忘的事（先停旧进程、等端口真正释放、确认真的起来了、日志写 data/logs）。注释 13-14：不停旧进程的话新进程因端口占用启动失败但旧进程还在响应 = "改了代码却没生效"，最费解的一类问题
- `start.sh:143`：`python -u` 不缓冲，否则日志文件长时间是空的像是卡住了
- `start.sh:152-165`：启动后轮询 `/api/health` 最多 20 秒；进程活着但健康检查不过 → 打印最后 20 行日志
- `start.sh:53-55`：用 lsof 而非 /bin/ps（部分环境不可用）
- `_fatal_message` 之外还有 `test_start_script_matches_doc`(test_stage6_reliability.py:~985)：断言文档提到的 flag 代码里确实实现

### 6.29 测试中用 `__new__` 手工构造 + getattr 兜底
session.py:362-364：部分测试用 `__new__` 手工构造会话对象、不走 `__init__`，属性可能不存在，所以 `_send_audio`、`end_turn`(528)、`response_pending`(778) 等处用 `getattr(self, ..., default)` 兜底。

### 6.30 后台任务集合防 GC
session.py:181-184：`self._bg_tasks` / `self._correction_tasks` 保存 task 引用并 `add_done_callback(discard)`，避免 asyncio task 被 GC 提前回收。
