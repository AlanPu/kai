## 1. 需求（确认版）

| # | 需求 | 落实方式 |
|---|---|---|
| 1 | 输入：主题 / 段落 / 文章 / 网址 | 统一走「内容分析 → 生成话题计划」 |
| 2 | 主动引导我说，但要**多给我说的机会** | 引导语简短，AI 说话占比目标 ≤ 40% |
| 3 | 语法纠错 + 地道表达建议 | 界面实时显示，不打断 |
| 4 | 发音：明显单词错误才纠正 | 分级判定，口音问题默认不纠 |
| 5 | 角色：陪练 / 一对一辅导老师 | 写进系统提示词 |
| 6 | 历史记录 + 个性化 | SQLite + Markdown 个人画像 |

### 已确认的关键决策

- **存储**：SQLite（会话/统计数据）+ Markdown（个人画像，可读可改）
- **纠错时机**：界面实时显示 + 语音里自然带一句（**不打断**）
- **时长**：约 30 分钟，到点自动结束并生成报告
- **推进**：分阶段，每阶段可运行可验收

### ⚠️ 需求冲突及解决

原选择「语音实时纠正」与「多给我说的机会」「不要频繁打断」直接矛盾。
**已解决**：AI 不插话；纠错显示在侧栏，并允许 AI 在**你说完一段后**自然地
把正确说法嵌进回应里，例如：

> "Oh, you went to the park? Nice — by the way, we say *I went*, not *I go*."

这样既实时又不打断。

#### 迁移策略：清空旧数据

原库有 52 次会话、11 条画像。迁移时**直接清空**，不分配给某个用户。
理由：旧数据是在"只有一个人"的前提下产生的，
归到谁头上都是猜的，猜错会污染画像。清空前自动备份到
`data/app.db.bak-<时间戳>`，想找回来随时可以。

SQLite 不支持给已有表加 `NOT NULL + REFERENCES` 列，
也不支持改 `UNIQUE` 约束，所以用重建表的方式：
`PRAGMA foreign_keys = OFF` → 改名旧表 → 建新表 → 删旧表。
`turns` / `corrections` 也要跟着重建，因为它们外键指向 `sessions`。

#### 声纹窗口从 1 秒改到 2 秒

这是本轮最有价值的发现。用两个不同 TTS 音色实测
（同人 vs 异人各取多段算余弦）：

| 窗口 | 同人均值 | 异人均值 | 间隔 |
|---|---|---|---|
| 0.5s | 0.477 | 0.322 | 0.156 |
| 1.0s | 0.582 | 0.372 | 0.210 |
| 2.0s | 0.672 | 0.422 | 0.249 |
| 3.0s | 0.745 | 0.458 | 0.287 |

1 秒时同人最低 0.358、异人最高 0.511 —— **重叠**，
阈值 0.5 下同人只有 67% 能过、异人误收 11%。
改 2 秒后同人 100% 通过（最低 0.747），
异人最高 0.655 仍在阈值以下。

顺带校准了两组拍脑袋定的参数：

- `MIN_COHERENCE` 0.45 → 0.42（同人最低 0.485，留余量）
- 质量分档 `0.75/0.60` → `0.70/0.55`
  （实测同人均值才 0.644，原门槛下**永远评不上"好"**）

这些数值连同来历都写进了 `tests/test_stage7_users.py` 的回归测试 ——
它们太容易被后续改动"顺手调一下"。

## 4.1 阶段 6 发现的真实问题（都已修复）

阶段 6 的 30 分钟稳定性测试是本项目最有价值的一步 ——
它暴露了三个只有长时间运行才会出现的问题，
其中两个是此前完全不知道的严重缺陷。

### 问题 1：服务端关闭会话后程序继续空转
Qwen 在 300 秒无有效语音输入后关闭会话并报 `user_idle_timeout`，
但服务器只把错误转发给前端就 return 了，接着又空转 24 分钟 ——
用户对着一个已死的连接说话，程序显示一切正常。

**修复**：区分致命/非致命错误，致命错误抛 `SessionFatal`
终止会话并如实告知用户；同时新增暂停/恢复，
让中途离开不再触发这个问题。

### 问题 2：用户一场练习里只能被识别一次（最严重）
`input_audio_buffer.speech_started` 表示"用户开始说话"，
代码却当成"AI 开始说话"，置 `_model_speaking = True`。
而 `push_audio` 在该标志为真时丢弃全部音频，该标志又只在
`response.done` 复位 —— 于是用户说完第一句后音频全被丢掉，
不产生 response，也就永远等不到 `response.done`，形成死锁。

**修复**：`speech_started` 时置 `_model_speaking = False`
（语义是"轮到用户"），并新增 `user_speech_starts` 计数器 ——
这个数字只涨到 1 就是同一个 bug 复发的信号。

### 问题 3：会撞上 Qwen 的 audio item 上限而断线
Qwen 每条会话最多 320 条 audio item（实测约 12.5 分钟到顶），
超出直接报 `Too many audios` 并断开，练习被硬生生截断。

**修复**：上下文轮转 —— 接近上限时主动重连，
把最近 12 轮对话写成摘要放进新 instructions，
用户感受是一句话的停顿。两个实现坑：
1. 轮转不能在 Qwen 的 recv 回调里执行（会掐断接收循环），
   只能置标志由 timer 循环消费；
2. 重连后必须重新 `request_response()`，
   因为 Realtime API 永远不会自己开口。

**阈值标定**：服务端报 320 时我只数到 91 条（比例约 3.5:1，
因为服务端的 item 还含 AI 输出与 VAD 碎片），
阈值定为 60，测试里固化了这个标定防止被调高。

## 阶段 8：修复 AI 不主动接话 ✅

**现象**：用户说完一两句后停下，AI 就一直沉默，必须再说一句「继续」才往下走。
用户反馈"不像真人对话"。

**排查过程**：

直接连 Qwen 原始 WebSocket 打印全部事件，看到关键事实 ——
`input_audio_buffer.speech_stopped` 和 `committed` 都正常到达，
但**永远没有 `response.created`**。

也就是说：`turn_detection` 里配的 `create_response: True` 在 Qwen 上并不生效，
服务端只做 VAD 切分，不会自动生成回复。而项目代码只处理了
`speech_started`（用户开始说），没有任何地方在"用户说完"时主动触发回应。

**验证过的错误改法**（都试过，都不行）：

| 试法 | 结果 |
|---|---|
| 只改 `create_response: True` | 无效，本来就是 True |
| 改指令去掉"回答要短/别填沉默" | 无效，与指令无关 |
| 发 `response.create` 但不 commit | 无效，服务端忽略 |
| commit 后立刻 `response.create` | 无效，音频 item 还没落库 |
| **commit → 等 0.5 秒 → `response.create`** | **✅ 成功** |

**最终改法**（`app/services/session.py` + `app/core/realtime.py`）：

1. 新增 `is_speech_stopped()`，识别"用户说完"
2. 收到该事件后异步执行 `_respond_after_turn()`：
   先 `input_audio_buffer.commit`，等 0.5 秒，再 `response.create`
3. 期间若用户又开口（`_model_speaking`）或会话已结束，则放弃触发

**实测结果**：用户说一句后完全不做任何操作，AI 主动接话并追问
（`Nice, parks are a great way to start the day. What did you two end up ...`）。

**为什么以前的测试没发现**：soak 测试只统计"轮数"，
AI 不说话时轮数仍然在涨（因为用户还在说），所以指标是绿的。
这次是用户从体感上发现的 —— 说明自动化指标不能替代真人试用。

### 阶段 8 补丁：修掉新引入的崩溃

上一个修复（AI 主动接话）引入了两个新问题，用户很快遇到了
「会话被服务端中断（invalid_request_error）」。

**根因**：接话逻辑里无条件调用 `input_audio_buffer.commit`。
commit 空缓冲是**硬错误**，不是无操作：

```
Error committing input audio buffer: buffer too small, or have no audio.
```

而 VAD 对咳嗽、碰麦、键盘声都会报 `speech_stopped`，
那些时刻缓冲区是空的 —— 一次误触发就 commit 一次空缓冲。

**放大成崩溃的原因**：这个错误的 code 是 `invalid_request_error`，
而它被列在 `FATAL_CODES` 里，于是直接被当成"服务端关掉了会话"，
整场练习终止。实际上连接完好，继续对话毫无问题。

**两处修改**：

1. 新增 `_sent_audio_since_commit` 标志：只有真的送过音频才 commit。
   在 `_send_audio()` 置位，commit 时清零。
2. 把 `invalid_request_error` 从 `FATAL_CODES` 移除。
   它太笼统，把客户端小失误和真正的会话终止混为一谈；
   真正不可恢复的（`user_idle_timeout` / `invalid_api_key` /
   `insufficient_quota` / `session_expired`）本来就单独列着。

**验证**：模拟连发 6 个极短噪声脉冲（不构成语音），
日志里 `buffer too small` 出现 0 次，会话不中断；
同时确认正常说一句话后 AI 仍然主动接话（没把功能修坏）。
新增 2 个回归测试，都通过回退代码验证过会失败。

**教训**：这次的 bug 是上一次修复**引入**的，而我只测了
"正常路径能不能接话"，没测"异常输入会不会崩"。
VAD 误触发是必然会发生的输入，不是边界情况。

## 阶段 9：修复声纹导致的对话卡顿 ✅

**用户反馈**：「经常出现声纹无法识别的提示，然后 AI 半天没反应。
等我说『继续往下说』，它才响应上一句，然后把我打断。
不知道是 AI 响应的问题，还是麦克风采集的问题。」

**答案：都不是。是声纹的缓冲策略问题。**

### 根因

声纹每次判定需要攒满 `window_sec = 2.0` 秒音频。
原实现在「判定未知」时**把音频压住不发**，等攒够 `MAX_PENDING` 块才兜底放行。

致命的算术错误：`MAX_PENDING = 100` 块是按 **20ms/块**估算的，
但浏览器 AudioWorklet 实际每块 **128 采样 @16kHz = 8ms**。
所以兜底阈值实际只有 `100 × 8ms = 0.8 秒`，
**小于声纹窗口 2 秒** —— "攒够就放行"永远发生在判定仍为未知时。

### 造成的现象（实测复现，21 秒连续语音）

| 指标 | 旧实现 |
|---|---|
| 第一块送达 Qwen 的延迟 | **2.0 秒** |
| 实际送达比例 | 84% |
| 送达形态 | 切成 **20 段**碎块，平均每段 0.88 秒，中间有空洞 |

碎片化音频的后果：Qwen 的 VAD 把每个碎片末尾当成「用户说完了」
→ 生成回应；下一个碎片又被当成「用户又开始说」→ 打断刚生成的回应。

这精确对应用户描述的三件事：
「声纹无法识别」提示 + AI 半天不吭声 + 突然响应上一句并打断我。

### 改法（用户选择：优先流畅）

声纹只用于**否决**，不再用于**放行**：
- 明确判定为他人 → 丢弃（这个保护保留）
- 判定未知 → **立即放行**（不再压着等）

顺带修掉 `blocked_sec` 里同样按 0.02 秒/块计算的问题，
引入 `CHUNK_SEC = 128/16000` 常量统一换算，避免再次出现
"按错误的块大小估算"这类 bug。

### 实测对比

| 指标 | 旧 | 新 |
|---|---|---|
| 首块延迟 | 2.0 秒 | **0.096 秒** |
| 送达比例 | 84% | **97%** |
| 送达形态 | 20 段碎块 | **2561 块连续，无空洞** |

`voiceprint_stuck` 提示随之废弃（未知不再是异常状态，不需要打扰用户）。

### 测试改动说明

`test_stage3_voice.py` 里有 3 个测试**断言的是旧行为**
（"未知期间音频必须攒着"）。这不是测试写错了，而是本次
**刻意改变了设计权衡**，所以同步改写了断言，并把取舍理由
写进 docstring —— 避免以后有人以为这是回归又改回去。

同时新增"缓冲不能无限堆积"的不变量测试。

## 阶段 10：改成「按住空格说话」✅

用户在实测后提出：

> 简单一点，当我说话的时候，我会按住空格键，说完我会释放。
> 所以，不按空格的时候，你不用采集我的声音。

### 为什么这个改法是对的

前面几个阶段一直在和 VAD（语音活动检测）搏斗 —— 服务端要靠它猜
"用户说完没有"。这个猜测本身就是所有问题的源头：

| 猜错的形态 | 用户看到的现象 |
|---|---|
| 半句话被当成说完 | AI 抢着回应 |
| 用户接着说被当成抢话 | AI 刚生成的回应被打断 |
| 一句话被重复报 speech_stopped | 重复 response.create 报错 |
| 静音/噪声被当成说话 | 空 commit 报 "buffer too small" |

push-to-talk 把"猜"彻底去掉：**按下 = 我开始说，松开 = 我说完了。**
回合边界由用户掌握，服务端不需要任何推断。

意外的好处：不按空格时前端完全不上行音频，
连背景噪音都进不来，声纹误判的机会也一并消失了。

### 具体改动

**前端**（`app/web/index.html`）
- `keydown`/`keyup` 监听空格（用 `event.code === "Space"`，
  避免输入法和键盘布局干扰），按下/松开驱动 `pttDown()`/`pttUp()`
- AudioWorklet 回调里加闸门：`if (pttActive && !holding) return;`
  —— 不按空格时**一个字节都不上行**
- 松开后延迟 250ms 再断句：麦克风音频分块上行且有缓冲，
  松手瞬间最后几十毫秒还在路上，立刻断句会吃掉句尾
- 常驻绿色提示条显示"按住说话，松开表示说完了"，按下时高亮
- 窗口失焦时兜底松手（否则切走时 keyup 收不到，麦克风一直开着）

**后端**
- 新增 `turn_end` 指令 → `ConversationSession.end_turn()`：
  先把缓冲里剩的音频 flush 掉，再触发 AI 接话
- `turn_detection.create_response` 改为 **False**：
  实测 Qwen 本来就不遵守这个开关，但留着有害 ——
  服务端哪天真的开始遵守它，就会按 VAD 猜的断句点抢答
- `speech_stopped` 分支**不再**自动接话（只更新前端指示状态）
- 引入 `is_turn_race_error()`：把
  "already has an active response" 和 "buffer too small"
  识别为可自愈的回合竞态，记 info 而不是弹给用户看
- 删掉已废弃的 `commit_audio()`（服务端自己会 commit，
  我们再 commit 就是空提交）

### 实测（3 轮完整对话）

```
⌨️  按下空格，开始说（4.0秒）
⏹  松开空格 → turn_end
   转写: Hello. I went to the park yesterday with...
★ AI #1: Hey! Today we're chatting about weekend plans—
★ AI #2: Nice! You went to the park with your friend ye
★ AI #3: Sounds like a nice way to spend the day. Did y

用户 3 轮 / AI 接话 3 次 / 前端报错 0 次
回合竞态 0 / 致命错误 0 / buffer too small 0
```

### 测试改动说明

`test_stage7_users.py` 里有 4 个测试断言的是**旧的 VAD 触发设计**
（"speech_stopped 时要 commit + response.create"）。这不是测试写错了，
而是设计被 push-to-talk 取代，所以同步改写了断言，并把
"为什么放弃 VAD 断句"的实测记录写进 docstring，
避免以后有人当成回归又改回去。

新增测试：`end_turn` 存在且先 flush 再接话、`turn_end` 指令被处理、
`create_response` 为 False、`commit_audio` 已删除、
回合竞态错误的识别与"先分类再通知用户"。
已验证分别回退这两处都会让对应测试失败。

## 阶段 11：修复「听不到 AI 的语音」✅

用户反馈：改成按住空格说话之后，**听不到 AI 的语音**了。

这是上一阶段引入的回归，两个原因叠加：

### 原因 1：用 `ctxOut.close()` 来"停声"

前端的 `stopPlayback()` 原本这样实现：

```js
function stopPlayback() {
  playHead = 0;
  if (ctxOut) {
    try { ctxOut.close(); } catch (e) {}
    ctxOut = new AudioContext({ sampleRate: OUT_RATE });  // ← 问题在这
  }
}
```

`close()` 是**异步**的，而紧接着 `new AudioContext()` 在浏览器里
经常处于 `suspended` 状态 —— 于是之后所有 AI 音频**静默播放**，
用户什么都听不到。

修法：停声只停播放源（`playingSources` 里逐个 `stop()`），
保留 `ctxOut` 不动。另外加 `ensureOutCtx()`，每次播放前检查
上下文状态，`closed` 就重建、`suspended` 就 `resume()`。

### 原因 2：`user_speaking` 会掐断 AI 的声音

前端一收到服务端的 `user_speaking`（VAD 报告"检测到人声"）
就调 `stopPlayback()`。但 VAD 对**噪声、甚至 AI 自己的尾音**
都会触发 —— AI 刚开口就被打断，用户根本听不全。

修法：`user_speaking` 只熄灭指示灯，不再掐断声音。
抢话打断只由「**按下空格**」这个明确动作触发 ——
那是用户的真实意图，不会误判。

### 验证

服务端下发的音频本身是好的（实测 25 块 / 186240 采样 /
7.76 秒真实语音，峰值 15871），问题完全在前端播放路径。

### 测试

新增 4 个测试锁住正确行为：
- `stopPlayback` 不能出现 `close()`
- `user_speaking` 分支不能调 `stopPlayback`
- 按下空格必须调 `stopPlayback`（真实抢话）
- `enqueueAudio` 必须走 `ensureOutCtx`

已验证改回有 bug 的写法会让对应测试失败。

顺带修了测试自身的一个坑：断言"某处没有调用 X"时，
解释性注释里提到 X 会导致误判。新增 `_web_code()`
先剥掉 JS 注释再做判断。

## 阶段 12：冷场时 AI 主动找话题 ✅

用户反馈：

> 在一段对话以后，如果我不主动说，AI 就会一直在等我。
> 我希望在冷场的时候，AI 能够主动找话题跟我说。

这是「按住空格说话」的必然副作用：回合完全由用户发起，
用户不开口，AI 就永远不说话。安静本身没错，但用户卡住想不出
句子时会一直干等，练习就停在那里。

### 时间为什么定 15 秒

真人对话里 15 秒刚好是"对方在等你开口"，再长就像冷场，
再短就变成催促 —— 而用户需要时间组织英文句子，催太紧反而说不出来。

最初定的 20 秒，用户实际用下来觉得偏长（"现在 20 秒好像有点长了"），
改成 15 秒。

实际上感知到的等待是 **15～20 秒**：`_timer_loop` 每 5 秒轮询一次，
所以触发时刻落在 15 秒之后的第一个 5 秒刻度上。这是刻意的 ——
多等最多 5 秒换来的是不必为每个会话开一个精确计时器。

### 说话方式

第一次：温和地接着上一句换个角度追问。
第二次起：主动引入相关的新话题，避免在同一个点上打转
（那会让冷场更尴尬）。

两种情况都明确禁止说"你还在吗"、"怎么不说话了"这类扫兴话术 ——
指令里写死 `Do NOT ask whether they are still there`。
最多连续救场 6 次，之后停下，不刷屏。

### 排查过程中发现的真 bug

为了做冷场救场，反而挖出一个更严重的问题：**AI 经常根本没回应用户**。

现象：用户说完，AI 不接话也不报错，日志里只有
`Conversation already has an active response`。

根因链条：

1. 前端改成按住空格后，只在按住时上行 `input_audio_buffer.append`；
2. 原先依赖服务端 VAD 在 `speech_stopped` 时自动 commit，
   但这条在 push-to-talk 下不再可靠 —— 实测送上去 3 秒音频
   （30 块），**转写始终不出现**；
3. 没有 commit 就没有音频 item，`response.create` 被服务端
   静默吞掉；
4. 而我们的 `_response_pending` 去重标志在等一个永远不来的
   `response.created`，于是之后所有回合都被当成"重复"丢弃，
   冷场救场也一起失效 —— **会话静默死锁**。

修法：
- `end_turn()` 显式 `commit_audio()`。语义收紧为
  "松开空格 = 明确的提交信号"，且**只在确实发过音频时才提交**
  （空提交会回 `buffer too small`，这是当初删掉 commit 的原因）。
- `_response_pending` 加超时（12 秒）自动作废，卡死的回合能自愈。

这个 bug 在写冷场救场之前就存在 —— 只是"AI 不说话"很容易被
当成"它在等我"，直到我要求它主动开口才暴露出来。

### 实测

```
第 1 轮说完 → ★ AI: Nice, you went to the park. By the way, we usually...
第 2 轮说完 → ★ AI: That sounds really peaceful. Did you just relax, or...
（此后沉默）
💬 冷场 22s → ★ AI: So, what's the first thing you do when your weekend...
💬 冷场 23s → ★ AI: Let's switch gears: tell me about a time you changed...
💬 冷场 23s → ★ AI: Who's the person you most look forward to spending...

用户 3 轮 / AI 开口 7 次 / 主动找话题 4 次 / 报错 0 次
```


### 补修：为什么用户实测「停下 20 秒 AI 没接上」

上线后用户反馈：

> 我停下了 20 秒，AI 并没有自然接上。

我的自动化测试全绿，但真人用就是不行 —— 又是同一类错误：
测试跑了正常路径，没跑真实使用路径。查出两个叠加的 bug。

**bug 1：前端 push-to-talk 闸门从来没生效**

`pttActive` 这个变量声明了，判定逻辑也写了：

```js
if (pttActive && !holding) return;   // 不按空格就不上行
```

但**没有任何一处把它置为 true**。于是条件永远为假，闸门形同虚设，
麦克风从进入练习那一刻起就一直在上行音频（绝大部分是静音）。
我之前读到这里时只看到"逻辑写对了"就放过了 —— 没检查这个开关
是谁打开的。**声明了但没赋值的开关，是最难看出来的一类 bug。**

**bug 2：静音也算"用户有动静"**

`push_audio()` 一进来就无条件 `self.touch()`，把冷场计时清零。
麦克风上行是连续的，就算闸门修好了，松手前后也会有零散静音块
到达 —— 每一块都把计时重置，AI 永远等不到"满 20 秒"。

改成只有**检测到真实人声**（RMS 超过静音阈值）才 `touch()`。
未开声纹时没有 verifier 帮忙判断，就自己按音量判断，
静音直接不上行也不计时。

### 这次的教训

两个 bug 都是「静音被当成了用户说话」。这类问题的共同点是
**服务端永远看不到"没发生的事"** —— 只有静音持续涌进来时才会
暴露。所以新增的测试特意**主动灌静音流**：

```
说完一轮后持续上行静音 → 冷场 21s → AI 主动找话题 ✅
```

另外补了一条前端测试，专门检查 `pttActive = true` 真的存在
且发生在 worklet 绑定之前。三条新测试都验证过：
把对应修复回退掉，测试立刻失败。

### 测试

新增 8 个：冷场阈值、指令禁止"你还在吗"、连续冷场换策略、
不打断 AI 说话、催促次数上限、暂停时不催、_timer_loop 确实调用、
等待标志超时作废。

其中 `test_turn_end_commits_then_responds` 特意写成**行为测试**
（用假对象跑真实调用顺序），而不是检查源码文本 ——
文本断言会被注释里的同名字样骗过，这个文件已经踩过一次。
已验证把 commit 去掉会让它失败。

## 阶段 13：模型全部改为可配置 ✅

用户要求：

> 你不要自己选模型，你要通过配置让我自己来设置。

原先 `QWEN_MODEL` / `TEXT_MODEL` / `TEXT_BASE_URL` 虽然已经读了环境
变量，但**没写进 `.env.example`** —— 用户翻遍配置也看不到它们存在，
等于没有。另外转写模型 `qwen3-asr-flash-realtime` 是真写死在代码里的。

改动：
- 新增 `QWEN_ASR_MODEL`（转写模型），从 Settings 读取，代码里不再写死
- `.env.example` 补齐全部五项模型配置，并说明**语音模型和文本模型是
  两件独立的事**（各自决定什么功能可用）
- 启动时打印实际生效的模型，配置错了不用等到练习中途才发现
- `SETUP.md` 增加"换模型"章节，含"想换成别的厂商"的说明

顺带纠正了一个文档错误：原来写着"转写模型固定不可改"，已经不准了。

一个容易被忽略的事实：**语音模型和文本模型共用同一个 API Key**，
不需要分别申请。所以"只选了一个模型"通常不会真的发生 ——
但两者失效的影响面不同：文本模型挂了仍然能对话，只是材料准备失败。
