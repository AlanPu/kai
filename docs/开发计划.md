## 1. 需求（确认版）

| # | 需求 | 落实方式 |
|---|---|---|
| 1 | 输入：主题 / 段落 / 文章 / 网址 | 统一走「内容分析 → 生成话题计划」 |
| 2 | 主动引导我说，但要**多给我说的机会** | 引导语简短，AI 说话占比目标 ≤ 40% |
| 3 | 语法纠错 + 地道表达建议 | 界面实时显示，不打断 |
| 4 | 发音：明显单词错误才纠正 | 分级判定，口音问题默认不纠 |
| 5 | 角色：陪练 / 一对一辅导老师 | 写进系统提示词 |
| 6 | 历史记录 + 个性化 | SQLite + Markdown 个人画像 |

### 已确认的关键决策

- **存储**：SQLite（会话/统计数据）+ Markdown（个人画像，可读可改）
- **纠错时机**：界面实时显示 + 语音里自然带一句（**不打断**）
- **时长**：约 30 分钟，到点自动结束并生成报告
- **推进**：分阶段，每阶段可运行可验收

### ⚠️ 需求冲突及解决

原选择「语音实时纠正」与「多给我说的机会」「不要频繁打断」直接矛盾。
**已解决**：AI 不插话；纠错显示在侧栏，并允许 AI 在**你说完一段后**自然地
把正确说法嵌进回应里，例如：

> "Oh, you went to the park? Nice — by the way, we say *I went*, not *I go*."

这样既实时又不打断。

#### 迁移策略：清空旧数据

原库有 52 次会话、11 条画像。迁移时**直接清空**，不分配给某个用户。
理由：旧数据是在"只有一个人"的前提下产生的，
归到谁头上都是猜的，猜错会污染画像。清空前自动备份到
`data/app.db.bak-<时间戳>`，想找回来随时可以。

SQLite 不支持给已有表加 `NOT NULL + REFERENCES` 列，
也不支持改 `UNIQUE` 约束，所以用重建表的方式：
`PRAGMA foreign_keys = OFF` → 改名旧表 → 建新表 → 删旧表。
`turns` / `corrections` 也要跟着重建，因为它们外键指向 `sessions`。

#### 声纹窗口从 1 秒改到 2 秒

这是本轮最有价值的发现。用两个不同 TTS 音色实测
（同人 vs 异人各取多段算余弦）：

| 窗口 | 同人均值 | 异人均值 | 间隔 |
|---|---|---|---|
| 0.5s | 0.477 | 0.322 | 0.156 |
| 1.0s | 0.582 | 0.372 | 0.210 |
| 2.0s | 0.672 | 0.422 | 0.249 |
| 3.0s | 0.745 | 0.458 | 0.287 |

1 秒时同人最低 0.358、异人最高 0.511 —— **重叠**，
阈值 0.5 下同人只有 67% 能过、异人误收 11%。
改 2 秒后同人 100% 通过（最低 0.747），
异人最高 0.655 仍在阈值以下。

顺带校准了两组拍脑袋定的参数：

- `MIN_COHERENCE` 0.45 → 0.42（同人最低 0.485，留余量）
- 质量分档 `0.75/0.60` → `0.70/0.55`
  （实测同人均值才 0.644，原门槛下**永远评不上"好"**）

这些数值连同来历都写进了 `tests/test_stage7_users.py` 的回归测试 ——
它们太容易被后续改动"顺手调一下"。

## 4.1 阶段 6 发现的真实问题（都已修复）

阶段 6 的 30 分钟稳定性测试是本项目最有价值的一步 ——
它暴露了三个只有长时间运行才会出现的问题，
其中两个是此前完全不知道的严重缺陷。

### 问题 1：服务端关闭会话后程序继续空转
Qwen 在 300 秒无有效语音输入后关闭会话并报 `user_idle_timeout`，
但服务器只把错误转发给前端就 return 了，接着又空转 24 分钟 ——
用户对着一个已死的连接说话，程序显示一切正常。

**修复**：区分致命/非致命错误，致命错误抛 `SessionFatal`
终止会话并如实告知用户；同时新增暂停/恢复，
让中途离开不再触发这个问题。

### 问题 2：用户一场练习里只能被识别一次（最严重）
`input_audio_buffer.speech_started` 表示"用户开始说话"，
代码却当成"AI 开始说话"，置 `_model_speaking = True`。
而 `push_audio` 在该标志为真时丢弃全部音频，该标志又只在
`response.done` 复位 —— 于是用户说完第一句后音频全被丢掉，
不产生 response，也就永远等不到 `response.done`，形成死锁。

**修复**：`speech_started` 时置 `_model_speaking = False`
（语义是"轮到用户"），并新增 `user_speech_starts` 计数器 ——
这个数字只涨到 1 就是同一个 bug 复发的信号。

### 问题 3：会撞上 Qwen 的 audio item 上限而断线
Qwen 每条会话最多 320 条 audio item（实测约 12.5 分钟到顶），
超出直接报 `Too many audios` 并断开，练习被硬生生截断。

**修复**：上下文轮转 —— 接近上限时主动重连，
把最近 12 轮对话写成摘要放进新 instructions，
用户感受是一句话的停顿。两个实现坑：
1. 轮转不能在 Qwen 的 recv 回调里执行（会掐断接收循环），
   只能置标志由 timer 循环消费；
2. 重连后必须重新 `request_response()`，
   因为 Realtime API 永远不会自己开口。

**阈值标定**：服务端报 320 时我只数到 91 条（比例约 3.5:1，
因为服务端的 item 还含 AI 输出与 VAD 碎片），
阈值定为 60，测试里固化了这个标定防止被调高。

## 4.2 最终验收（额度恢复后、用当前代码重跑）

30 分钟连续会话，脚本模拟真人说话节奏：

| 指标 | 结果 |
|---|---|
| 时长 | **1790 秒（29.8 分钟）** |
| 轮数 | **289 轮** |
| 转写 | 我 215 句 / AI 74 句 |
| 用户发言占比 | **66%** |
| 纠错 | **46 条**（语法 17 / 用词 27 / 流畅 2） |
| 上下文轮转 | **3 次**（每次 60/320） |
| 服务端告警 | **0 条** |
| 内存 | **46 → 46 MB** |

`✅ 全程无错误、无断线`

### 这一轮补上的东西

1. **HTTPS 启动**（`--ssl`）—— 文档里一直写着相关命令，
   但代码根本没实现，照做会启动失败。已实现并验证
   局域网地址可访问。
2. **稳定性测试统计纠错** —— 之前完全不统计，
   需求 2 的核心功能在最重要的测试里是盲区。
   现在每次跑都会报条数。
3. **测试前先探活** —— 有一次端口上留着旧进程，
   新进程 bind 失败，于是 30 分钟测试跑的是旧代码，
   结论全部作废。现在连不上就直接退出。

### 纠错链路实测

喂入含真实语法错误的音频：

```
I go to park yesterday with my friend. He go to school every day.
I very like play basketball.
```

得到：

```
📝 [grammar/critical] I go to park yesterday    → I went to the park yesterday
📝 [grammar/critical] He go to school every day → He goes to school every day
📝 [grammar/critical] I very like play basketball → I really like playing basketball
```

前端侧栏与后端入库均已验证收到。

| 风险 | 状态 | 应对 |
|---|---|---|
| 30 分钟长连接断开 | ✅ 已解决 | 上下文轮转（阈值 60）+ 致命错误如实告知 |
| Qwen 320 条 audio item 上限 | ✅ 已解决 | 主动轮转；兜底把 `Too many audios` 归为可恢复 |
| 用户中途离开导致会话被关闭 | ✅ 已解决 | 暂停/恢复（暂停不计时、不收音频） |
| 纠错延迟高，体验差 | ✅ 已解决 | 纠错异步进行，不阻塞对话 |
| 实时纠错 API 调用费 | ✅ 已解决 | 按句批量提交，不逐字调用 |
| 个人画像越写越乱 | ✅ 已解决 | 分类白名单 + 置信度递增 + 注入上限 25 条 |
| 音频计费不可控 | ⚠️ 部分 | 有费用统计，但**是估算值**（音频可能按时长计费） |
| 发音评估深度不足 | ⚠️ 未做 | 目前靠转写文本推断，非音素级评估 |
| 手机浏览器未测试 | ⚠️ 部分 | HTTPS 启动已实现并验证（局域网地址可访问），但无手机实机可测 |
| 连接以异常方式断开时无人察觉 | ✅ 已解决 | 接收任务挂 done 回调 + `is_connection_lost()` 看护；服务端补发 `aborted` |

### 明确不做或做不到的（如实说明）

- **声纹不是安全级身份验证**：有预热期误接受，换麦克风/环境会退化，
  感冒时基本失效。它只是"避免 AI 把自己的声音当成用户"的辅助手段。
- **费用是估算**：Realtime 音频可能按时长而非 token 计费，
  给出的数字仅供参考。单次 30 分钟在亚元级。
- **音素级发音评估未做**：需求 3 说"特别明显的发音错误才纠正"，
  当前实现是从转写文本反推（如转写出现明显错词），
  不足以判断口音细节 —— 但这恰好符合"不要频繁打断"的要求。

```bash
# 启动（默认 8000 端口）
```

## 8. 后续可以做的（未做）

按价值排序，供你自己决定：

1. **真机走一遍完整 30 分钟** —— 所有测试都是脚本模拟，
   真人说话的停顿、口头禅、自我纠正还没被覆盖。
2. **手机浏览器验证** —— HTTPS 已实现并在局域网验证过（`--ssl`），
   但没有真机测过麦克风权限和 iOS Safari 的兼容性。
3. **复习机制** —— 现在纠错只存在库里，
   没有"把上周的高频错误再考我一遍"这类功能。
   数据都在（`corrections` 表 + `top_error_words()`），接上就行。
4. **音素级发音评估** —— 需要额外接评测 API，
   当前只用转写文本反推。
