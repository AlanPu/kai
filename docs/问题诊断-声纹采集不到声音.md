# 声纹"采集不到声音"的诊断记录

## 症状

```bash
.venv/bin/python diagnose_voiceprint.py --compare-devices
```

三台设备全部报「采集不到声音 / 没测出结果」，但音量条**明明在动**。

## 真相：声音采到了，是被声纹代码丢掉了

### 根因：float32 与 int16 的单位不匹配

`core.py` 的 `SpeakerVerifier.feed()` 里有个静音门槛：

```python
if float(np.sqrt(np.mean(audio ** 2))) < 200:
    return None          # ← 判定"太安静"，直接返回
```

**这个 200 是按 int16 量级（±32768）定的**，但实际喂进来的音频
可能是 float32 量级（±1.0）：

| dtype | 范围 | 典型 RMS | 能否过 200 门槛 |
|---|---|---|---|
| int16 | ±32768 | ~1700 | ✅ 能 |
| **float32** | **±1.0** | **~0.03** | ❌ **永远不能** |

而 `sounddevice` 的 InputStream 回调给的就是 **float32**，
`diagnose_voiceprint.py` 直接把它喂给 `feed()` → **RMS 恒 < 200
→ 永远返回 None → 永远出不了分**。

表现就是"采集不到声音"，但音量条正常。

### 为什么之前没发现

- **命令行版**（`realtime_qwen.py`）把音频转成 int16 才喂 → 一直正常
- **网页版**（`server.py`）也是 int16 → 也正常
- **只有诊断脚本**直接喂 float32 → 独独它挂

这是个典型的「单位在不同调用点不一致」的错误。

## 修复

`core.py` 的 `feed()` 现在按实际 dtype 归一化：

```python
peak = float(np.max(np.abs(audio)))
if peak <= 1.5:          # 判定为 float32 (±1.0) 量级
    rms *= 32768.0       # 换算到 int16 量级再比较
if rms < 200:
    return None
```

这样 **float32 和 int16 两种输入都能正确处理**。

## 修复过程中额外发现并修掉的问题

| # | 问题 | 后果 |
|---|---|---|
| 1 | `score_audio` 要求整 1 秒才打分 | 录音 0.9 秒 → **0 段结果**，误报"太安静" |
| 2 | 提示写死"太安静" | 实际可能是"太短"，**误导排查方向** |
| 3 | `--secs` 允许 < 1.5 秒 | 声纹按 1 秒窗口出分，太短必然无结果 |
| 4 | RMS 用整数格式打印 float32 | 显示为 `0`，看起来真像没声音 |
| 5 | 进度条刷新率 0.12s + sleep(40ms) | 打印跳跃，看起来像卡住 |
| 6 | `compare_devices` 里 `meta` 未赋值就使用 | `UnboundLocalError` 崩溃 |

## 验证

| 场景 | 修复前 | 修复后 |
|---|---|---|
| float32 音频喂入 | 永远 None，buf=0 | ✅ 1.0 秒即出分 |
| int16 音频喂入 | 正常 | ✅ 仍正常 |
| 0.9 秒录音打分 | 0 段 | ✅ 有结果 |
| 服务端端到端 | 正常 | ✅ 仍正常（转写+下行 14 块） |

## 教训

**"没声音"和"代码把声音丢了"看起来一模一样。**
凡是"采集不到"的问题，必须先用最小手段确认信号是否真的进了程序
（这里是打 RMS 和峰值），再怀疑采集设备。

另外：**同一份数据在不同调用点用了不同单位**，是极难发现的错误 ——
因为每一处单独看都"对"。修法不是改调用点，而是让被调方自己归一化。
