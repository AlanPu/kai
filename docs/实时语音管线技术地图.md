## 1. 一句话语音的端到端数据流

### 上行（麦克风 → Qwen）

| 阶段 | 位置 | 具体参数 |
|---|---|---|
| getUserMedia | `app/web/index.html:528` | `{echoCancellation:true, noiseSuppression:true, autoGainControl:true, channelCount:1}` — 三项**全开**。注释 `:502-505` 解释：三项都关会导致 AI 听见自己（自问自答）、音量过低 VAD 不触发；`noiseSuppression` 是唯一影响声纹的一项但实测影响很小 |
| 输入 AudioContext | `index.html:511` | `new AudioContext({sampleRate: IN_RATE})`，`IN_RATE = 16000`（`index.html:364`） |
| 采集节点 | `index.html:540` | 运行时拼出的 AudioWorklet `PCM` processor，`process()` 里 `postMessage(ch.slice(0))` — **每个 render quantum 一帧**。Web Audio 的 quantum = **128 采样 @16 kHz = 8 ms**（服务端也是这么算的，见 `app/services/session.py:58-60`） |
| 重采样 | `index.html:535, 537-542` | `ratio = ctxIn.sampleRate / IN_RATE`。因为 `new AudioContext({sampleRate:16000})` 已经让浏览器重采样到 16 k，`ratio` 通常 = 1，这段是**兜底**的最近邻重采样（`out[i] = f32[floor(i*ratio)]`） |
| 转 int16 | `index.html:568` | 手写 `Int16Array` 循环，`v<0 ? v*32768 : v*32767` |
| 上行发送 | `index.html:570` | `ws.send(i16.buffer)` — **裸二进制帧**，没有 JSON 包装。每帧 = 128 采样 = 256 字节 |
| 服务端接收 | `app/api/server.py:743-755` | `_recv_loop` 用 `msg["bytes"]` 分流，二进制 → `sess.push_audio()` |
| 声纹闸门 | `session.py:247-347` | 见第 3 节 |
| 送 Qwen | `session.py:358-364` → `realtime.py:242-246` | `{"type":"input_audio_buffer.append","audio":base64(PCM)}` |
| Qwen 配置 | `realtime.py:205-206` | `input_audio_format:"pcm16"`, `output_audio_format:"pcm24"` |

**重要**：浏览器实际送的是 **8 ms / 256 字节** 的块，而
`app/core/audio.py:18-20` 定义的 `BLOCK_MS=20 / IN_BLOCK=320 /
IN_BLOCK_BYTES=640` 是**给桌面 Python 客户端（sounddevice 路径）用的官方推荐值，
在 Web 路径上从未被引用**（grep 确认全仓库无其它引用点）。Web 路径完全靠 128 采样的
worklet 量子。改 `audio.py` 的常量不会影响网页端。

### 下行（Qwen → 扬声器）

| 阶段 | 位置 | 参数 |
|---|---|---|
| Qwen 下发 | `realtime.py:431-442` | `response.audio.delta` → base64 解码，**24 kHz PCM 原始字节** |
| 转发 | `session.py:408-412` | `extract_audio_delta` 命中就 `audio_out_blocks += 1` 并 `on_client({"type":"audio","pcm":_b64(audio)})` |
| 服务端出口 | `server.py:667-671` | `ws.send_json(msg)` — **JSON + base64** |
| 浏览器解码 | `index.html:395, 718-720` | `b64ToBytes` → `enqueueAudio` |
| int16→float32 | `index.html:456` | `f32[i] = i16[i] / 32768` |
| 建 AudioBuffer | `index.html:457` | `ctxOut.createBuffer(1, f32.length, OUT_RATE)`，`OUT_RATE = 24000`（`index.html:364`） |
| 排队播放 | `index.html:437-442` | `playHead` 排程：`if (playHead < currentTime) playHead = currentTime + 0.02`（20 ms 提前量），`src.start(playHead)`，然后 `playHead += buf.duration` — 无抖动缓冲，纯首尾相接 |
| 输出 AudioContext | `index.html:503` | `new AudioContext({sampleRate: 24000})`，三层解锁保护（见第 5 节） |

> ⚠️ 两条方向封装方式完全不同：**上行是裸二进制帧，下行是 JSON + base64**。很容易搞混。

## 2. Push-to-talk 状态机

### 状态变量（`index.html:378`）

```js
let holding = false, pttActive = false;
```

- `pttActive`：闸门总开关，**只置位从不清零**。在 `startMic()` 里置 `true`
  （`index.html:552`），`cleanup()` 不复位它。
- `holding`：用户此刻是否按着空格。

### 隐含的第三个状态：`pttTailTimer`（`index.html:594`）

松手后进入 **TAILING** 状态（250 ms），此时 `holding=false` 但 `turn_end` 还没发。

### 转换表

| 事件 | 位置 | 动作 |
|---|---|---|
| `startMic()` 完成 | `index.html:552` | `pttActive = true`（进入 IDLE/可说话） |
| `keydown` Space | `index.html:637` | `typingInField()` 检查 → `e.preventDefault()`（防页面滚动 `:619`）→ `e.repeat` 直接 return（`:620`）→ `pttDown()` |
| `pttDown()` | `index.html:596` | 守卫：`!running \|\| paused \|\| !ws \|\| readyState!==1` 返回（`:575`）；`if (holding) return`（`:576`）；清 `pttTailTimer`（`:578`）；**`stopPlayback()` 立即掐掉 AI 语音**（`:580`）；UI 加 `live`（`:581-582`），hint = "正在说…"（`:583`） |
| worklet `onmessage` 闸门 | `index.html:557` | `if (pttActive && !holding) return;` — **不按空格一个字节都不上行** |
| `keyup` Space | `index.html:646` | 同 guard → `pttUp()` |
| `pttUp()` | `index.html:608` | `holding=false`；UI 复位（`:589-590`）；hint = "松开空格 = 说完了，AI 正在听…"（`:591`）；**起 250 ms 定时器**（`PTT_TAIL_MS = 250`，`index.html:593`），到点后 `ws.send({"type":"turn_end"})`（`:593-599`） |
| `window.blur` | `index.html:680` | `if (holding) pttUp()` — 兜底：切窗口时 keyup 收不到 |
| 服务端 `paused` | `index.html:778` | `if (holding) pttUp()` + `stopPlayback()` |
| `cleanup()` | `index.html:846` | `running=false`，关 mic/ctx。**`holding` 和 `pttActive` 都不复位** — 见第 5 节 |

**PTT 尾巴延迟的由来**：麦克风音频分块上行带缓冲，松手瞬间最后几十毫秒还在路上，
立刻断句会吃掉句尾。

### 其它快捷键

- **C 键**（`index.html:643-654`）：`isPromptKey`（`:639-641`，用 `event.code === "KeyC"`
  不受输入法/大小写影响）→ 守卫 `!running \|\| paused`（`:646`）、`e.repeat`（`:647`）、
  放过 ⌘/Ctrl/Alt 组合键以免吞掉复制（`:648`）、**`if (holding) return`**（`:651`）
  → `ws.send({"type":"prompt"})`（`:652`）

### 服务端侧对称逻辑

`_handle_cmd`（`server.py:785-811`）：`"turn_end"` → `sess.end_turn()`（`:790-795`）；
`"prompt"` → `sess.prompt()`（`:796-799`）。

`ConversationSession.end_turn()`（`session.py:501-540`）：

1. `_flush_pending()`（`:511`）— 防止声纹未决时丢掉句尾
2. **仅当 `_turn_audio_blocks > 0`** 才 `commit_audio()`（`:528-530`）。判据注释
   `:524-527` 说明为什么不能用 flush 前后差值：声纹关闭时音频在 `push_audio`
   阶段就直发了，差值永远得 0
3. 归零 `_turn_audio_blocks`（`:539`）
4. `_maybe_respond()`（`:540`）

## 3. 声纹闸门

### 判定函数

`SpeakerVerifier.feed(samples)` — `app/core/voiceprint.py:80-120`。

### 阈值链

| 常量 | 值 | 位置 | 含义 |
|---|---|---|---|
| `threshold` | **0.5** | `voiceprint.py:66`（默认参数）；`session.py:94`；`server.py:922` | 余弦相似度 ≥ 此值算"本人" |
| `window_sec` | **2.0 s** | `voiceprint.py:67` | 判定窗口 = `IN_RATE * 2 = 32000` 采样（`:89`） |
| `history` | **3** | `voiceprint.py:68` | 多数表决窗口 |
| `SILENCE_RMS` | **200**（int16 量级） | `voiceprint.py:27` | 窗口整体 RMS 低于此不判定 |
| `VOICE_RMS_FLOOR` | **120** | `session.py:57` | **逐块**门槛，低于此只进待定缓冲不算"用户有动静" |
| `MIN_COHERENCE` | **0.42** | `enroll.py:58` | 录入时与已有样本的均值相似度下限 |

> **门槛不对称**：`120`（块级，进 pending）和 `200`（窗口级，不判定）差 80。
> 块级低门槛是为了抓句间停顿的尾巴，窗口级高门槛是为了避免噪声产生随机向量。

### feed() 的三态返回（`voiceprint.py:80-120`）

1. 样本不足 → `None`（`:90-91`）
2. 静音（`rms < 200`）→ `None`（`:96-97`）
3. 抽出向量算分：余弦 = `dot(proto, normalize(v))`（`:103-108`）
   - 逐次判定 `is_me = score >= 0.5`（`:115`）
   - 推入 history，超长丢最旧（`:116-118`）
   - **返回 `sum(history) > len(history)/2`**（`:120`）— 3 票里要 **≥2** 才算 True

### 在管线中的位置：`ConversationSession.push_audio()`（`session.py:247-347`）

```
push_audio(pcm bytes)
├─ 261: if paused/ended/no rt → return
├─ 275: if _model_speaking → return          ← AI 说话期间整个丢弃
└─ if verifier:
   ├─ 279: np.frombuffer(int16)
   ├─ 283-288: rms <= 120 → _pending.append + _trim_pending → return   [静音]
   ├─ 291: self.touch()                     ← 只有真实人声才清冷场计时
   ├─ 293: verdict = verifier.feed()
   ├─ 295-320: verdict is None → **_flush_pending() + 直发**          [判不出→放行]
   ├─ 322-333: verdict is False → 丢弃 _pending + on_client("voiceprint_skip")
   └─ 336: verdict True → _flush_pending()
   else (无 verifier): 342-345: rms<=120 → return; 否则 touch() + 直发
347: _send_audio(pcm)
```

**"判不出就放行"的确切位置：`session.py:295-320`**。注释 `:296-317` 是全文件最长的
一段解释，核心是：原来这里"压着不发"，导致（a）用户开口后最多 2 秒 Qwen 收不到声音；
（b）攒够后批量补发变成带空洞的碎片；（c）Qwen VAD 把每个碎片末尾当断句 → 生成回应 →
下一个碎片又打断。结论是 **"声纹只用来否决，不用来放行"**（`:315-317`）。

### 待定缓冲 `_pending`（`session.py:155, 349-356`）

- `MAX_PENDING = 500`（`session.py:64`）
- `_flush_pending()`（`:349-352`）：取出并逐块 `_send_audio`，**保持顺序**
- `_trim_pending()`（`:354-356`）：`pop(0)` 丢最旧
- 注释 `:61-63` 明确：**这个上限现在只用于裁剪静音段，不再是"攒够就放行"的兜底**

### `verifier.reset()` 的调用点

- `session.py:486-488`：`response.done` 时清空 —— "避免把自己的尾音算进判定"
- `session.py:747-748`：上下文轮转后
- `voiceprint.py:75-78`：只清 `buf` 和 `history`，**不清 `last_score` / `judged`**

### `rms()` 的量级自适应（`audio.py:23-38`）

`peak <= 1.5` 判为 float32(±1.0) 量级则 `r *= 32768`。注释 `:24-29` 记录了坑：
门槛按 int16 定（如 200）但 sounddevice/numpy 给 float32，差 32768 倍。

### 录入侧（独立管线，`/ws/enroll`）

- `EnrollmentSession.commit()`（`enroll.py:174-229`）校验顺序：超 12 s 截断（`:193-195`）
  → RMS 门槛（`:198-200`）→ 最短 2 s（`:201-203`）→ 抽向量失败（`:206-207`）
  → **与已有样本均值 < 0.42 拒绝**（`:211-219`）
- `MIN_SPEECH_SEC=2.0` / `MAX_SPEECH_SEC=12.0` / `MIN_SAMPLES=3`（`enroll.py:43,45,62`）
- 阈值 0.42 的实测依据在 `enroll.py:52-58` 的表格：同人内部两两最低 0.485 /
  异人最高 0.360，中间有真空带
- `prototype()`（`enroll.py:267-280`）：多样本平均后再归一化
- **占位原型**：录入阶段只用到 `verifier.ex`（提取器），所以 `server.py:867-876`
  用 `_dummy_prototype()` 造了个 192 维单位向量
- 存在 `users.py:174-176` 的注释：落盘时**额外存了所有原始样本向量**（`embeddings`
  字段），为将来改阈值/多原型匹配免去重录

## 5. 非显眼的实现细节（会绊人的地方）

### 5.1 事件名不匹配 / 双向兼容

| 位置 | 问题 |
|---|---|
| `server.py:954-958` | 录入协议前端发 `{"type":"end"}`，早期脚本发 `{"cmd":"end"}`。**两个都认**：`action = (cmd.get("cmd") or cmd.get("type") or "").strip()`。注释明确：曾只认 `cmd`，导致网页点「读完了」被静默忽略（不报错不回应，看起来像"点了没反应"），而脚本测试一切正常 |
| `server.py:602` | WS 建连失败时发 `{"type":"error","error":"用户不存在..."}` — **`error` 是字符串**；而正常运行时 `session.py:384` 发的是 `{"type":"error","error":err}`，`err` 是 **dict**。前端 `index.html:795` 用 `((e && (e.message||e.code)) || e || "未知错误")` 兼容了两种形态 — **这是隐式契约，不是巧合** |
| `index.html:725` | `user_speaking` 事件的处理：注释 `:706-712` 说**这里不再调 stopPlayback()**。原来一收到就掐 AI 声音，但 VAD 对噪声、甚至 AI 自己的尾音都会触发 → AI 刚开口就被打断。抢话现在只由 `pttDown()` 触发（`:580`） |
| `server.py:656-660` | 服务端发 `{"type":"voiceprint_missing"}`，前端 `onServer` **没有对应分支** → 被静默忽略 |
| `server.py:803` | 服务端支持上行 `{"type":"status"}` 回 snapshot，前端**从不发送** |
| `server.py:787-789` | 服务端支持上行 `{"type":"cancel"}` → `rt.cancel_response()`，前端**从不发送** |

### 5.2 AudioContext 不能 close 的坑（最重要的一条）

`index.html:475` 注释：抢话时**不能**用 `ctxOut.close()` 来"停声"。close() 是异步的，
紧接着新建的 AudioContext 在部分浏览器会处于 suspended → AI 语音再也播不出来
（用户原话："我听不到 AI 的语音"）。正确做法是只 `s.stop()` 每个 `BufferSource`，
保持 ctxOut 可用。

`stopPlayback()` 实现（`:459-466`）：遍历 `playingSources` 逐个 stop+disconnect，
清空数组，`playHead = 0`。

**自动播放策略三层解锁**（`index.html:492`）：

1. 没有/closed → 新建
2. suspended → `resume()`
3. 兜底：注册 `{once:true}` 的 `pointerdown` + `keydown` 监听器。注释 `:477-480` 解释：
   `resume()` 返回 Promise，若调用时已脱离手势上下文（比如中间 await 过网络请求）会被拒绝

**一次性诊断日志**（`index.html:748`）：第一次收到 `audio` 时打印 ctxOut 状态/
采样率/播放源数/playHead，并 `window.__audioDiag` 加锁。这是专门为"听不到 AI 语音"
这个 bug 留的取证代码。

### 5.3 Buffer 累积 / 顺序保证

- **上行**：worklet 每 8 ms 一个 `postMessage`，`ws.send(i16.buffer)`。`i16.buffer` 是
  新建的 `Int16Array`，无共享内存问题（`:543-548`）
- **待定缓冲** `_pending`：`_flush_pending()`（`session.py:349-352`）保持顺序逐块发
- **下行播放队列**：`playHead` 单调递增，
  `if (playHead < currentTime) playHead = currentTime + 0.02`（`index.html:437`）—
  这 20 ms 是防"playHead 落后于 currentTime"导致丢音
- `playingSources` 用 `src.onended` 做自清理（`index.html:467`）—
  否则长会话会累积几千个已结束的 BufferSource 引用

### 5.4 顺序隐患（有注释解释的）

| 位置 | 隐患与解法 |
|---|---|
| `realtime.py:190-196` | `_recv_task` 是 fire-and-forget，不挂 done_callback 的话 `_recv_loop` 里冒出的 `SessionFatal` 会静静存在 task 对象里永远没人发现。注释记录：**实测这个坑让一次会话在服务端已死之后又空转了 24 分钟** |
| `session.py:371-380` | 同理 — `realtime.py:_handle` 的 `on_event` 调用必须让 `SessionFatal` 透传，被吞掉的话接收循环不终止，用户看到"报错了但画面卡住不动" |
| `session.py:389-396` | 遇到 `too_many_audios` **只能置标志 `_want_rotate = True`**，不能直接关连接 — 注释：在这里关会掐断正在跑本回调的 `_recv_loop`，异常冒泡会让整个会话被判异常结束。真正的重连由 `_timer_loop`（`server.py:822-824`）执行 |
| `session.py:424-433` | **严重历史 bug，注释保留着**：`speech_started` 曾经误设 `_model_speaking = True`。而 `push_audio` 在 `_model_speaking` 为真时丢弃所有音频，该标志只在 `response.done` 复位 → 用户说第一句后再也不能说话，不产生 response 也就永远等不到 `response.done` — **死锁** |
| `session.py:561-571` | `_respond_after_turn()` 硬编码 `await asyncio.sleep(0.5)` — 注释：`speech_stopped` 之后服务端还要把音频 item 落库，太早 `response.create` 会被忽略（现象就是 AI 不吭声）。0.5 秒实测够用 |
| `session.py:164-180` | `_response_pending` **必须能超时复位**（12 s，`response_pending_timeout`）。注释：发了 `response.create` 但服务端根本没产生 response（半句话/音频太短/空缓冲），`response.done` 永远不来 → 之后所有回合被当重复静默丢弃 |
| `session.py:776-788` | `response_pending()` 里 `since == 0` 视为"刚刚发起"不算超时 — 因为外部可能直接置标志没有时间戳 |
| `realtime.py:386-417` | `close()` 必须限时。注释：实测 `ws.close()` 挂住 >8 s 不返回（要等对端回 close 帧，而对端可能已经不理我们了）。超时后取 `ws.transport` 调 `abort()` 强断 |

### 5.5 `pttActive` 只置位不复位

`pttActive = true` 在 `startMic()`（`index.html:552`）设置，注释 `:526-529` 说明了
为什么**必须**置上：

> 之前漏了这一行，导致闸门形同虚设、麦克风一直在上行静音，服务端把每一块静音都当成
> "用户有动静"从而不断重置冷场计时，AI 永远等不到"冷场"（用户反馈：停下 20 秒 AI
> 也不接话）。

配套的服务端保护：`session.py:264-291` 注释 + `VOICE_RMS_FLOOR = 120` 逐块门槛 —
**只有 `rms > 120` 的块才 `touch()`**（`:291`、`:345`）。

但 `cleanup()`（`index.html:846`）**不复位 `holding` 和 `pttActive`**。`running=false`
是实际的第二道闸（`index.html:557` 检查 `!running`）。所以 `resume()` 后如果用户仍
处于某种边角状态，`pttDown()` 会因 `!running` 守卫（`:597`）返回，`holding` 保持
false — 实际安全，但这是个隐性契约。

### 5.6 数值转换的不对称

| 位置 | 转换 |
|---|---|
| `index.html:546`（上行） | `v<0 ? v*32768 : v*32767` |
| `index.html:456`（下行） | `i16[i] / 32768` |
| `audio.py:46`（`to_int16`） | `np.clip(a, -32768, 32767)`，但缩放用 `* 32768.0`（正负不对称） |

上行用 32767/32768 分段处理是为了对称映射；下行统一除 32768。三处不完全一致，
但没有实际影响。

### 5.7 静音块的 `stats` 统计口径

`session.py:58-60`：`CHUNK_SEC = 128 / 16000`（8 ms）。`blocked_sec` 的算法（`:324`）
是 `len(self._pending) * CHUNK_SEC + CHUNK_SEC` — 只统计被**丢弃**的 pending 块，
不含当前块。

### 5.8 `int16` 解码的 numpy 陷阱

`server.py:941-944` 注释：

> 必须显式按 int16 解释：直接喂 bytes 会被 numpy 当成 uint8 数组，特征提取器会把它
> 当字符串解析而报错

代码是 `np.frombuffer(msg["bytes"], dtype=np.int16)`。注意：**字节数必须是偶数**才不会
有截断 —— 前端发的是 `Int16Array` 的 `.buffer`（`index.html:570, 1520`），天然对齐。

### 5.9 `AUDIO_ITEM_ROTATE_AT = 60` 的标定

`session.py:38-54` 长注释：

- Qwen 每会话最多 **320 条** audio item，超出报 `Too many audios` 并断线
  （实测约 12.5 分钟到顶）
- 但服务端计的是**全部** item（含 AI 输出 + VAD 内部片段），客户端只数
  `input_audio_buffer.committed`
- 30 分钟实测：服务端报 320 时客户端只数到 **91**（比例 3.5:1）
- 所以阈值必须远低于 91，取 **60**（约服务端 210 条时轮转，留 110 余量）
- 注释 `:51-53`：**"提前轮转的代价只是 1~2 秒停顿，撞上限的代价是断线，两者不对等
  —— 宁可早转"**；并说 150 那次失败就是因为没留够余量

轮转时用 `db().list_turns()` 取最近 12 条拼成 `## 刚才的对话` 塞进新 instructions
（`session.py:713-723`），且**必须重新触发 response.create**（`:750-758`，
否则轮转完一片沉默）。

### 5.10 音色两套清单

`voices.py:8-12` 注释：**对话音色（`CHAT_VOICES`）和 TTS 音色（`TTS_VOICES`）只有
部分重叠**。拿只在对话那套的音色去合成试听会报 `Invalid voice specified` ——
那不是名字写错，是 TTS 模型根本不带这个音色。

`server.py:332-346` `voice_sample` 显式检查 `can_sample()` 并返回人类可读原因，
前端 `index.html:1400-1402` 据此把不可试听的音色标 `—` 并在 note 里解释。

音色优先级：网页选择 > `.env` 的 `QWEN_VOICE` > 默认 `"Tina"`（`config.py:52`）。
网页选择持久化到 `data/voice_override.txt`（`server.py:317-329`），**且会覆盖 .env**
（`server.py:304-309` 注释解释：用户点了但重启后悄悄变回去，看起来就是"点了没用"）。
删除该文件可恢复。
