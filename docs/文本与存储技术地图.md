## 1. 配置层（`app/core/config.py`）

### 1.1 加载机制

- `PROJECT_ROOT = Path(__file__).resolve().parents[2]` — `app/core/config.py:16`。**注意是 parents[2]，不是 parents[1]**：文件在 `app/core/`，parents[0]=`app/core`、parents[1]=`app`、parents[2]=仓库根。所有默认路径都基于它。
- `_load_dotenv()` — `config.py:19-28`，显式按 `PROJECT_ROOT/".env"` 加载，`override=False`（`config.py:23`）—— **真实环境变量优先于 .env**。整个 dotenv 逻辑包在 `try/except Exception: pass`（`config.py:24-25`），所以没装 python-dotenv 也不会炸。
- `load_settings(env: Optional[dict] = None)` — `config.py:98-100`。`env` 参数可注入字典，便于测试（`e = env if env is not None else os.environ`）。全代码库**只有这一处**读环境变量（`grep os.environ|getenv` 在 `app/` 下只命中 `config.py:100`）。
- `get(key, default)` — `config.py:102-104`：`v = e.get(key); return v if v else default` —— **空字符串等同于未设置**，会退回默认值。这是 `IDLE_NUDGE_MAX=""` 被测试覆盖的原因（见 §6.2）。
- `get_path(key, default)` — `config.py:106-108`：非空则 `Path(v)`，否则用默认 `Path`。
- `ssl_context()` — `config.py:31-42`：强制使用 certifi 证书链，失败退回 `create_default_context()`。被 `llm.py:62`、`content.py:170`、`api/server.py:65` 共用。

## 2. LLM 客户端（`app/core/llm.py`）

### 2.1 API 风格：**OpenAI 兼容模式（compatible-mode），非原生 DashScope SDK**

- 默认端点 `https://dashscope.aliyuncs.com/compatible-mode/v1`（`config.py:60-61`）。
- 请求形状 `{base_url}/chat/completions`（`llm.py:51-52`），payload `{model, messages, temperature, max_tokens}`（`llm.py:42-47`）。
- 鉴权 `Authorization: Bearer <DASHSCOPE_API_KEY>`（`llm.py:55`）。
- **零第三方依赖**：只用标准库 `urllib.request`（`llm.py:13-14`），类注释明确「极简 OpenAI 兼容客户端，只用标准库，不引入额外依赖」（`llm.py:27`）。`requirements.txt` 也印证没有 openai SDK。
- 模型名取 `model or self.s.text_model`（`llm.py:43`）—— 三个文本特性共用同一个模型，靠参数覆盖。

### 2.2 网络细节

- **主动绕过代理** — `llm.py:59-62`：`build_opener(ProxyHandler({}), HTTPSHandler(context=ssl_context()))`。注释「国内服务：绕过代理，否则可能失败」。`config.py` 的 HTTP(S)_PROXY 因此对文本链路无效。
- 默认 timeout 60s（`llm.py:29`），构造时可覆盖。
- 错误映射：`HTTPError` → `LLMError(f"HTTP {code}: {detail}")`，body 截断 500 字符（`llm.py:67-73`）；其他异常 → `LLMError(f"{type}: {e}")`（`llm.py:74-75`）。
- 响应解析：`data["choices"][0]["message"]["content"]`，KeyError/IndexError → `LLMError("响应格式异常: ...")`（`llm.py:77-80`），截断 300 字符。

### 2.3 两个公开方法

- `chat(messages, *, model=None, temperature=0.7, max_tokens=2048, json_mode=False)` — `llm.py:35-80`。凭据缺失时先抛（`llm.py:39-40`）。`json_mode=True` 时注入 `response_format={"type":"json_object"}`（`llm.py:48-49`）。
- `chat_json(messages, **kw)` — `llm.py:82-90`。强制 `json_mode=True`（`kw.setdefault`，`llm.py:88`），再走 `parse_json_loose`。

### 2.4 JSON 容错解析（`llm.py:93-129`）

`parse_json_loose(raw)` — `llm.py:100-115`。空串 → `LLMError("模型返回为空")`（`llm.py:107-108`）。`_candidates(text)` — `llm.py:118-129`，按顺序产出最多 4 个候选：
1. 原文（`llm.py:119`）
2. 去 ```json 代码围栏（正则 `_FENCE_RE` = `r"```(?:json)?\s*(.*?)```"`，`llm.py:97,121-123`）
3. 首个 `{` 到最后一个 `}`（`llm.py:125-128`）
4. 首个 `[` 到最后一个 `]`（同上）
全部失败 → `LLMError(f"无法解析为 JSON: {text[:300]}")`（`llm.py:115`）。

测试：`test_stage2_text.py:62-74`（4 个参数化用例 + 垃圾输入抛错）。

### 2.5 三份 JSON 输出契约（全部走 `chat_json`）

| 特性 | 契约形状 | temperature | max_tokens | 位置 |
|---|---|---|---|---|
| planner | `{background, opening, vocabulary[], topics[{title,prompt,why,level}]}` | 0.8 | 2500 | `planner.py:84-93`（提示词内的示例）/ `planner.py:132`（参数） |
| corrector | `{corrections[{kind,severity,original,suggestion,explanation,word,phonetic}]}` | 0.3 | 1200 | `corrector.py:69-78` / `corrector.py:113` |
| profile | `{facts[{category,key,value,confidence}]}` | 0.2 | 800 | `profile.py:66-67` / `profile.py:87-88` |

temperature 梯度（0.8 > 0.3 > 0.2）反映任务性质：备课要发散，纠错/画像要稳定。

## 3. 三个文本特性

### 3.1 Planner（`app/services/planner.py`）— 备课/生成话题

**数据模型**
- `Topic` — `planner.py:23-30`：`title`(中文标题)、`prompt`(英文引导句)、`why`(中文说明)、`level`(open/guided/followup，默认 `"open"`)。
- `Plan` — `planner.py:33-59`：`opening`(英文开场白)、`topics[]`、`vocabulary[]`(可能用到的词)、`background`(中文摘要)。
- `Plan.to_dict()` — `planner.py:42-48`；`Plan.from_dict()` — `planner.py:50-59`，**容错**：用 `{k: v for k, v in t.items() if k in Topic.__dataclass_fields__}` 丢弃模型多给的字段（`planner.py:56-57`）。

**Prompt 策略** — `SYSTEM_PROMPT`，`planner.py:62-94`（中文写给模型，角色=「英语口语陪练备课」）：
- 学生画像：中文母语者（`planner.py:64`）
- 三条诉求：主动引导、简短引导留说话机会、贴近生活（`planner.py:65-67`）
- 硬约束：4~6 个话题由浅入深（`planner.py:73`）；prompt 必须是一句英文且开放式，禁止 yes/no（`planner.py:74-76`）；要能让人说 3 句以上（`planner.py:77`）；优先「联系自身经历」的问法并给了 `Have you ever...` / `What do you usually do when...` 例（`planner.py:78-79`）；vocabulary 5~8 个（`planner.py:81`）
- 结尾「严格按下面的 JSON 输出，不要有任何额外文字」+ 完整示例（`planner.py:83-94`）

**`Planner.plan()` — `planner.py:103-137`**
- 入参 `content: Content`、`profile_summary: str = ""`、`n_topics: int = 5`
- 前置校验 `content.ok`，否则 `LLMError(f"输入内容不可用: {content.error}")`（`planner.py:112-113`）
- user 消息组装 `planner.py:115-125`：`素材类型：{kind}` → 可选 `标题：{title}` → `素材内容：\n{content.text[:8000]}`（**截断 8000 字符**）→ `请设计 {n_topics} 个话题。` → 若有画像则追加「【关于这位学生的已知信息】…请把话题往他感兴趣的方向靠」（`planner.py:121-125`）
- 后置：`_normalize` 后若 `not plan.topics` → `LLMError("模型未产出任何话题")`（`planner.py:135-136`）

**`_normalize()` — `planner.py:139-170`（模型输出容错）**
- 非 dict → `LLMError("计划格式错误: {type}")`（`planner.py:142-143`）
- topic 元素是**字符串**也能吃：包成 `Topic(title=t, prompt=t)`（`planner.py:148-150`）
- `prompt` 兼容别名 `question`（`planner.py:153`）；空 prompt 直接丢弃（`planner.py:154-155`）
- `title` 缺省回落到 prompt，截 80 字符（`planner.py:157`）
- vocabulary 去空截 10（`planner.py:162-163,168`）
- topics 截 `n_topics`（`planner.py:169`）

**质量校验（纯本地启发式）**
- `_OPEN_MARKERS` — `planner.py:178-181`：what/why/how/tell me/describe/imagine/which/who/where/what's/whats
- `_CLOSED_STARTERS` — `planner.py:183-187`：do you/does/did you/is/are/was/were/have you/has/can you/could you/would you/will you/should
- `is_open_question(prompt)` — `planner.py:190-204`：**含任一开放词即算开放**（`planner.py:202-203`），否则看是否以封闭词开头。注释 `planner.py:194-197` 记录了误判教训：`"Have you ever felt tension ...? What happened?"` 以 Have 开头但有追问，实际开放。
- `validate_plan(plan) -> list[str]` — `planner.py:207-220`：缺开场白（`:210-211`）、话题 <3（`:212-213`）、缺引导语（`:215-216`）、疑似封闭式（`:217-219`）。**空列表 = 没问题**。

**`build_tutor_instructions()` — `planner.py:227-304`：Plan → Realtime 系统提示词**
这是文本侧与语音侧的交接点，注释明说「集中体现需求 2/3/4/5」（`planner.py:233-238`）。固定段落：
- 角色（`planner.py:240-245`）
- **「Let the student talk (very important)」** — `planner.py:247-253`：回复 1-2 句、目标学生占 60% 时间、一次只问一个问题、不要用自己说话填满沉默、短答就温和追问
- **「Correcting mistakes」** — `planner.py:255-263`：说话中**不打断**，结束后自然织入**一条**纠正（带 `Oh, you went to the park?...` 示例，`:258-260`）、每轮至多一条、优先 recasting 而非讲规则
- **「Pronunciation」** — `planner.py:265-270`：只纠**明显**的词级误读（举例 think/sink），**不纠**口音/轻微错/语调，且绝不为发音打断
- 动态段：`## Today's material`（`planner.py:274-275`，来自 `plan.background`）、`## Topics to explore`（`planner.py:277-281`）、`## Vocabulary`（`planner.py:283-286`）、`## What you already know about this student`（`planner.py:288-294`，含 "Do not recite it back." `:292`）、`## Session`（`planner.py:296-303`，含 minutes）

**落库**：`Plan.to_dict()` 经 `db.save_plan(sid, plan.to_dict())` 写入 `sessions.plan_json`（`db.py:285-289`；调用点 `api/server.py:634`）。`json.dumps(..., ensure_ascii=False)`（`db.py:288`）。

**两条备课路径必须给出同一份计划**（曾长期不一致，是"多人画像混进同一份话题"的根因）：
| 路径 | 入口 | 用户来源 | 画像 |
|---|---|---|---|
| HTTP 预览 | `POST /api/prepare` → `prepare` | `_require_user(user)`，**无回退** | `store.summary(u.id)` |
| WS 开练 | `/ws/session` → `ws_session` | `user` 查询参数，**无回退** | 未命中缓存时才读，且与提示词**共用这一份** |

两者都传 `profile_summary=summary`。WS 里 `summary` 只读一次（`_server.py` `ws_session` 的"画像"段），分两次读会让话题按一个人的兴趣挑、开场却按另一个人的经历寒暄。
前端「生成话题」必须走 `api()` 包装（`index.html` `btnPrepare.onclick`）才会带上 `user=`；裸 `fetch` 会让服务端回退到"最近用过的那个人"。

**两次备课只算一次**：`app/services/plancache.py` 的 `PlanCache` 按 `(user_id, 内容指纹)` 记住 `/api/prepare` 的结果，WS 建连时命中即复用、不再调模型。设计要点：
- **不用 token**：`ws_session` 本来就收到 `content`（`server.py:584`），服务端能自己算出同一个键 —— 前端一行不用改，也就没有"忘了传 token"这种新的失效方式
- **键必须带 `user_id`**：两人练同一篇文章是常事，共用计划就又串味了
- **指纹只 strip，不归一大小写**（`content_fingerprint`）：`Remote work` 与 `remote work` 可能引出完全不同的话题
- **是缓存不是持久化**：不写库、不跨重启（`uvicorn.run` 单 worker，见 `app/__main__.py:65-73`）
- **失效**：`session._extract_profile` 画像更新后调 `invalidate_plan_cache`（`session.py`），删除用户时 `plan_cache().invalidate_user`

### 3.2 Corrector（`app/services/corrector.py`）— 语法纠错

## 5. `content.py`：抓取与内容提取（重点：注入风险）

### 5.1 类型判定

- `Content` dataclass — `content.py:32-44`：`kind`(topic/passage/article/url)、`raw`、`title`、`text`、`error`；`ok` 属性 = `error is None and text.strip()` 非空（`content.py:42-44`）。
- `is_url(s)` — `content.py:51-56`：`^https?://` 直接命中；否则 `^[\w-]+(\.[\w-]+)+([/?#].*)?$` **且不含空格**（`example.com/post` 算网址）。
- `normalize_url(s)` — `content.py:59-63`：无 scheme 则补 `https://`。
- `classify(raw)` — `content.py:66-90`：注释 `:69-70`「宽松优先，宁可判成文章也不要误判成主题」。空→topic；url→url；按 `[.!?。！？]+` 粗略数句（`:83`）；`len>=800 或 句数>=5` → **article**（`:86-87`）；`len>=120 或 句数>=2` → **passage**（`:88-89`）；else **topic**（`:90`）。
- `load_content(raw)` — `content.py:242-247`：url 走 `fetch_url`，其余直接 `Content(kind=kind, raw=raw, text=raw.strip())`。

### 5.2 SSRF 防护（`_assert_public_host`）

**刻意不用 `ipaddress.is_private`** — `content.py:97-99` 注释：「它会把 `2001::1` 这类正常公网 IPv6 判成 private（实测踩到），导致整站被拦」。改为**显式枚举网段**：
- `_BLOCKED_V4` — `content.py:100-112`：11 条：0.0.0.0/8、10/8、100.64.0.0/10（CGNAT）、127/8、169.254/16（链路本地，**含云元数据 169.254.169.254**）、172.16/12、192.0.0.0/24、192.168/16、198.18.0.0/15、224/4（组播）、240/4（保留）
- `_BLOCKED_V6` — `content.py:113-119`：5 条：`::/128`、`::1/128`、`fc00::/7`、`fe80::/10`、`ff00::/8`
- `_is_blocked` — `content.py:122-124`：按版本选网段表
- `_assert_public_host(url)` — `content.py:127-151`：`socket.getaddrinfo` 解析 → 收集全部地址 → **只有全部解析结果都是内网才拒绝**（`content.py:150`）。注释 `:133-137` 说明原因：「很多正常网站会同时解析出公网 IPv4 和一个内网标记的 IPv6，只要有公网地址就应该放行（实测 en.wikipedia.org 属于此类）」。异常：`网址缺少主机名`（`:139-140`）、`域名无法解析: {host}`（`:143-144`）、`域名无解析结果`（`:147-148`）、`拒绝访问内网地址`（`:150-151`）。

### 5.3 `fetch_url` — `content.py:154-185`

- `normalize_url` → `_assert_public_host`，失败时**返回 `Content(error=...)` 而非抛异常**（`content.py:157-160`），调用方靠 `content.ok` 判断
- 请求头 `User-Agent`（伪造 Chrome，`content.py:27-29`）与 `Accept-Language: en,zh;q=0.9`（`content.py:163-166`）
- **代理行为与 llm.py 不同**：`content.py:169-170` 只挂 `HTTPSHandler`，**不挂 `ProxyHandler({})`**，因此走 urllib 默认逻辑（读 HTTP(S)_PROXY 环境变量）。注释 `:167-168`：「外网站点走代理；国内直连。交给系统代理设置处理，但明确使用 certifi 证书链。」—— 这与 `llm.py:59-62` 的强制清空代理形成对照，也是 §1.5 中代理变量「对文本链路无效、对抓取链路有效」的依据。
- 默认 `timeout=25`（`FETCH_TIMEOUT`，`content.py:26`）
- 错误映射：`HTTPError` → `error=f"HTTP {e.code}"`（`:174-175`）；其他 → `f"{type(e).__name__}: {e}"`（`:176-178`）
- 提取不到正文 → `error="未能提取到正文（可能是动态渲染页面）"`（`content.py:181-183`）
- **成功时正文截断到 `MAX_CONTENT_CHARS = 20000`**（`content.py:25,185`），注释 `content.py:24`：「避免把整站导航都灌给模型」

### 5.4 `extract_article` — `content.py:203-230`

**刻意不引入 BeautifulSoup** — `content.py:207-208`：「标准库足够应付大多数文章页，且少一个依赖。提取质量不足时由模型兜底。」

正则表 `content.py:192-200`：
- `_SCRIPT_RE` = `r"<(script|style|noscript|svg|nav|footer|header|aside)\b.*?</\1>"`（`:192-194`）—— 删整块
- `_TAG_RE` = `r"<[^>]+>"`（`:195`）—— 删残余标签
- `_TITLE_RE` / `_H1_RE`（`:196-197`）—— 标题优先 `<title>`，取不到回退 `<h1>`
- `_BLOCK_RE` = `r"</(p|div|h[1-6]|li|br|tr)>"`（`:198`）—— 块级闭合标签转 `\n`，制造段落边界
- `_WS_RE` = `r"[ \t\u00a0]+"`（`:199`，含 NBSP）→ 空格
- `_MULTINL_RE` = `r"\n{3,}"`（`:200`）→ 压缩为 `\n\n`

流程：删 script 块 → 块标签转行 → 去标签 → `_unescape`（`html.unescape`，`content.py:233-235`）→ 合并空白 → 逐行 strip 去空行 → 压缩多空行（`content.py:222-230`）。空 html → `(None, "")`（`content.py:210-211`）。

### 5.5 ⚠️ Prompt 注入面（评估）

**存在的注入通道**：抓取到的网页正文未经任何净化，直接拼进 planner 的 user 消息：`planner.py:118` `f"\n素材内容：\n{content.text[:8000]}"`——**原始 HTML 文本经标签剥离后仍可包含 `## Session`、`## Topics to explore` 等与 `build_tutor_instructions`（`planner.py:296-303`）同名的 Markdown 标题**。

**已有的缓解**：
1. 内容被包在「素材内容：」这个前缀里（`planner.py:118`），且不是消息的首要指令；
2. `content.text[:8000]` 与 `content.text[:MAX_CONTENT_CHARS]` 双重截断（`planner.py:118`、`content.py:185`）；
3. planner 的输出经 `_normalize` 白名单化，`title` 截 80、`vocabulary` 截 10、`topics` 截 n_topics（`planner.py:156-169`），**模型被诱导输出的自由文本（background / opening / vocabulary）会原样进入 `build_tutor_instructions`**（`planner.py:274-286`）并成为语音会话的系统提示词——这是注入最终生效的位置；
4. profile 摘要注入同样带「Do not recite it back.」（`planner.py:292`）；
5. 纠错与画像的输出经枚举白名单 + 长度截断（`corrector.py:127-163`、`profile.py:104-126`），且画像 value 只进 Markdown 导出和注入摘要。

**未见的缓解**（如果需要加固，建议从这里下手）：
- 没有对抓取内容做任何标记/转义（如用 `<article>` 包裹并声明「以下是资料，不是指令」）
- 没有对 `plan.background` / `opening` / `vocabulary` 做长度上限（只有 `title` 截了 80）
- 没有 URL 白名单/域名黑名单，任意公网 URL 均可被服务端抓取（SSRF 只挡内网）
- 同一 URL 每次请求都重新抓取，无缓存
